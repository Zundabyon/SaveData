## サービス概要

SaveData は、**いつ・何歳の頃に・どんなゲームを遊んでいたのか**を記録し、振り返ることができるサービスです。

ゲーム体験を単なるプレイ記録として残すのではなく、**人生の年表の一部として保存し、再体験できること**を目指しています。

---

## このサービスを作った理由

子どもの頃に夢中で遊んだゲーム。学生時代に友人と語り合ったタイトル。大人になってから時間を作って遊んだ作品。

ゲームは、人生のさまざまなフェーズと深く結びついています。しかし既存サービスの多くは **「何を遊んだか」「どこまで進んだか」** に焦点を当てており、**「いつ・どんな気持ちで遊んだか」** は記録されにくいと感じていました。

私は、ゲームを単なる娯楽や消費コンテンツではなく、**人生の記憶として残せるものにしたい**と考えました。

同じゲームでも、年齢や環境が違えば受け取り方は変わります。その違いを可視化することで、**「自分だけの思い出」と「世代の共通体験」を同時に味わえるサービス**を作りたいと考え、開発に至りました。

## 使い方

### 1. アカウント作成

トップページから新規登録を行います。プレイヤー名・生年月日などを入力して、アカウントを作成します。

### 2. ゲームを登録

「ゲーム登録」から、以下の情報を入力できます。

<p align="center">
  <img src="app/assets/images/readme/game_howto.gif" width="800">
</p>

- ゲームタイトル
- プレイした年齢
- ハード / ジャンル
- 面白さ・難易度（５段階）
- 思い出メモ
- カバー画像（任意）

### 3. 年表で振り返る

登録したゲームは、**年齢順のタイムライン**として表示されます。自分のゲーム体験を、人生の流れに沿って振り返ることができます。

  <img src="app/assets/images/readme/topdemo.gif" width="800">
</p>

### 4. 詳細の確認・編集

各ゲームカードをクリックすると、以下の操作が可能です。

- 思い出の詳細表示
- 編集 / 削除
- 思い出のシェア機能（X に投稿）

## 技術的に工夫した点

### IGDB API × 多段階検索ロジック（課題解決の例）

ユーザーのゲーム登録にかかる時間が長く「登録しづらい」というフィードバックを受け、ゲーム情報取得 API「**IGDB API**」を導入しました。

しかし導入後、以下の課題が明らかになりました。

> - IGDB API は **英語タイトルにのみ対応**しており、日本語入力ではほぼヒットしない
> - **完全一致でないと検索結果に出てこない**（ファジー検索非対応）
> - 無料枠は **50件まで** というリクエスト制限がある

これらの課題に対し、以下の **4つの検索戦略を組み合わせて**対応しました。

#### 解決策 1：DeepL API との連携で日本語対応

日本語が入力された場合に、DeepL API で英語に変換してから IGDB を検索することで、日本語入力でも正確なタイトルを返せるようにしました。

#### 解決策 2：3種の検索ロジックでヒット率を向上

IGDB の完全一致依存を補うため、以下の3つのロジックを組み合わせました。

| 検索方法           | 内容                                     | 例                          |
| ------------------ | ---------------------------------------- | --------------------------- |
| 部分一致           | キーワードが含まれていればヒット         | `Dark` → `Dark Souls`       |
| 分割キーワード検索 | スペース区切りで複数ワードをそれぞれ検索 | `dark souls` → 個別にマッチ |
| スペース除去検索   | スペースなし表記にも対応                 | `Darksouls` → `Dark Souls`  |

#### 解決策 3：重複除去で 50件枠を有効活用

同一タイトルが複数ハード向けに存在する場合、制限内でより多くの **異なるゲームタイトル**を表示できるよう、重複を除去するロジックを実装しました。

#### 結果

- 画像・ジャンル・ハード情報を自動取得することで、入力ステップを大幅に削減
- 日本語入力でも精度の高い検索が可能に
- UI/UX 体験の大幅な改善を実現

## テスト

### テスト方針

「書けるから書く」ではなく、**「保守性と品質担保のために書く」** という思想でテストを設計しました。

### カバレッジ

SimpleCov を導入し、**テストカバレッジ率 93%** を達成しています。

### 外部API連携のテスト（WebMock）

外部APIとの通信をモックすることで、ネットワーク環境に依存しない安定したテストを実現しています。IGDB API の日本語翻訳フローや検索ロジックなど、**ビジネスロジックの中核にあたる外部API連携**に対してもテストを実装しています。

```ruby
# WebMockを使ったIGDB APIモックテストの例
RSpec.describe IgdbService do
  include WebMock::API

  describe '#search_games' do
    before do
      stub_request(:post, "https://api.igdb.com/v4/games")
        .with(
          body: /dark souls/i,
          headers: { 'Client-ID' => ENV['IGDB_CLIENT_ID'] }
        )
        .to_return(
          status: 200,
          body: [
            { id: 1, name: "Dark Souls", cover: { url: "//images.igdb.com/..." }, genres: [{ name: "RPG" }] }
          ].to_json,
          headers: { 'Content-Type' => 'application/json' }
        )
    end

    it 'ゲームタイトルで検索結果を返すこと' do
      result = IgdbService.new.search_games('dark souls')
      expect(result.first[:name]).to eq('Dark Souls')
    end
  end
end
```

## 技術選定理由

### フロントエンド：TailwindCSS

Rails との相性が良く、`rails tailwindcss:watch` と組み合わせることでリアルタイムに確認しながら開発できました。カスタムアニメーション（`@keyframes`）やグラデーション表現も柔軟に組み込めるため、RPG 風 UI/UX デザインとの相性も抜群です。

- **迅速な UI 開発**：クラスベースで細かい調整がしやすく、バックエンド実装に集中できる
- **一貫性のあるデザイン**：定義済みクラスとカスタムプロパティで、デザインの統一性を保ちやすい

### バックエンド：Ruby / Ruby on Rails

本サービスは CRUD 中心で、ユーザー・ゲーム・年表といったデータの関係性が明確なため、開発効率と保守性の観点から採用しました。Rails の MVC パターンや設計哲学（DRY / CoC）により、構造的に理解しやすく、チーム開発でも読みやすいコードを書きやすい点でも適していると感じています。

### データベース：PostgreSQL（Neon）

- **Render との親和性**：Render での PostgreSQL 運用実績が豊富で、デプロイ・運用が容易
- **Neon のサーバーレスアーキテクチャ**：無料枠で本番運用が可能。従量課金制のため、初期コストを抑えられる
- **Rails との相性**：Active Record が PostgreSQL の機能を十分にサポートしている

### 外部 API：IGDB API

#### 選定理由

ゲームのタイトル・カバー画像・ジャンル・対応ハード・発売年など、**登録に必要な情報を一括取得できる数少ない無料 API** として選定しました。

ゲーム情報 API を調査した際の比較は以下のとおりです。

| API            | 無料枠               | 日本語対応 | 取得できる情報                                       |
| -------------- | -------------------- | ---------- | ---------------------------------------------------- |
| **IGDB API**   | あり（月間上限あり） | ほぼ非対応 | タイトル・画像・ジャンル・ハード・発売年など豊富     |
| RAWG API       | あり                 | 部分対応   | タイトル・画像・ジャンルなど（ハード情報がやや弱い） |
| Giant Bomb API | あり                 | 非対応     | 情報量は多いが、レスポンス構造が複雑                 |

IGDB は **Twitch（Amazon傘下）が運営**しており、データの信頼性・網羅性が高く、カバー画像の品質も優れていました。日本語非対応という課題は DeepL API との組み合わせで解決する方針を立て、最終的に IGDB を採用しました。

#### 実装上の工夫

無料枠の **1リクエストあたり 50件制限** を最大限活用するため、重複ゲームタイトル（複数ハード版）を除去するロジックを実装し、より多くの異なるタイトルを返せるようにしています。

---

### 外部 API：DeepL API

#### 選定理由

IGDB API が日本語入力にほぼ非対応であるという課題を解消するために導入しました。ユーザーが日本語でゲームタイトルを入力した際に、英語へ翻訳してから IGDB へ検索をかけることで、検索精度を大幅に向上させています。

翻訳 API の比較は以下のとおりです。

| API                      | 無料枠               | 翻訳精度（ゲームタイトル）     | 導入のしやすさ             |
| ------------------------ | -------------------- | ------------------------------ | -------------------------- |
| **DeepL API**            | あり（月 50万文字）  | 高い（固有名詞・略称にも強い） | シンプルな REST API        |
| Google Cloud Translation | あり（月 50万文字）  | 標準的                         | GCP の設定が必要でやや複雑 |
| Amazon Translate         | あり（月 200万文字） | 標準的                         | AWS 設定が必要             |

ゲームタイトルは略称や造語が多く、翻訳精度が検索結果に直結します。実際に「ドラゴンクエスト」「スト2」など複数タイトルで比較検証した結果、**DeepL が最もゲーム固有名詞に強く**、精度が高いと判断しました。また、REST API のシンプルな設計で Rails への組み込みコストが低い点も採用理由のひとつです。

### 画像管理：Cloudinary

- 画像の最適化・リサイズが自動で行われ、ユーザーがアップロードした画像の表示速度が向上
- Active Storage との統合がスムーズで、導入コストが低い
- 無料枠で十分な容量を確保できる

### インフラ：Docker + Render

`Dockerfile.dev`（開発環境）と `Dockerfile`（本番環境）を分離することで、ローカル・本番間の環境差異を最小化しました。Render は GitHub 連携による自動デプロイが容易で、無料枠で PostgreSQL + Web サーバー運用が可能です。

### 認証：Devise + Google OAuth 2.0

Rails のデファクトスタンダードであり、Google 認証との統合が容易です。パスワードリセット・メール確認などの認証フローが標準実装済みで、セキュリティの担保と開発速度の両立を実現しています。

### メール送信：Resend

- 無料枠で十分な送信数を確保できる
- カスタムドメインに対応しており、メール到達率が高い
